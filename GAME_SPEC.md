# Фаза 0. Описание продукта и решений: офлайн-игра Memory

Дата: 10.11.2026
Статус: утверждено для реализации
Область: локальная логика игры на одном устройстве, пользовательские колоды, режимы игры, правила, ограничения первой версии, ADR по хранению изображений и импорту/экспорту.

---

## 1. Краткое описание продукта

Разрабатывается классическая игра на память — Memory / Concentration — для игры на одном устройстве без сервера и сетевой синхронизации.

Игрок или несколько игроков по очереди открывают по две карточки. Если карточки совпадают, они остаются открытыми и образуют пару, а игрок получает дополнительный ход. Если не совпадают, карточки закрываются, и ход передаётся следующему участнику.

Партия завершается, когда найдены все пары. В многопользовательских режимах победитель определяется по количеству собранных пар.

Поддерживаются пользовательские колоды двух типов:

1. Изображения — пользователь загружает картинки, каждая картинка образует пару.
2. Текст — пользователь вводит текстовые пары, например слова, термины, названия, буквы и т.п.

---

## 2. Цели первой версии

### Цели

1. Обеспечить полноценную офлайн-игру на одном устройстве.
2. Поддержать три режима:
   - один игрок;
   - несколько игроков по очереди, до 6 человек;
   - один игрок против бота.
3. Позволить пользователю создавать собственные колоды из изображений или текста.
4. Зафиксировать понятные правила игры и терминологию.
5. Определить ограничения по количеству карточек, пар, раскладке, таймеру и файлам.
6. Принять решение по локальному хранению пользовательских изображений и поведению после перезапуска приложения.
7. Сделать первую версию стабильной, простой и не требующей серверной инфраструктуры.
8. Убедиться, что колоды можно импортировать и экспортировать в JSON.

### Не цели первой версии

В первой версии сознательно не входят:

1. Онлайн-мультиплеер.
2. Аккаунты, авторизация, облачное хранение.
3. Синхронизация колод между устройствами.
4. Смешанные колоды, где одновременно используются и картинки, и текст.
5. Редактирование анимаций, тем, рубашек карточек.
6. Глобальные рейтинги и таблицы рекордов.
7. Несколько уровней сложности бота, если это не требуется для минимального баланса.
8. Восстановление активной партии после перезапуска приложения — в первой версии это ограничиваем отдельно.

## 3. Терминология

| Термин | Определение |
|---|---|
| Карточка | Один элемент игрового поля. Может быть закрыт, открыт или найден. Каждая карточка имеет ссылку на пару-шаблон. |
| Пара-шаблон | Элемент пользовательской колоды: одно изображение или одна текстовая запись. При подготовке партии из одного шаблона создаются две игровые карточки. |
| Пара | Две игровые карточки с одинаковым парой-шаблоном. Найденная пара остаётся открытой и засчитывается игроку. |
| Ход | Действие текущего игрока, в результате которого открываются две доступные карточки. Каждый ход учитывается в статистике. При совпадении игрок получает дополнительный ход. |
| Партия | Один игровой цикл: от перемешивания и выкладывания карточек до момента, когда все пары найдены. |
| Колода | Пользовательский набор пар-шаблонов. Колода может быть текстовой или графической. |
| Черновик | Статус колоды, который сохраняется, но не может быть использован для игры до перевода в статус «Добавлена». |
| Добавлена | Статус готовой колоды, которая доступна для выбора и запуска партии. |
| Раскладка | Схема игрового поля в виде строк и столбцов. Произведение строк и столбцов должно быть равно количеству игровых карточек. |
| Текущий игрок | Участник, за которым сейчас очередь хода. |
| Передача хода | Переход очереди к следующему участнику после несовпадения карточек. |
| Дополнительный ход | Право текущего игрока открыть ещё две карточки после найденной пары. |
| Хотсит | Режим, когда несколько игроков играют по очереди за одним устройством. |
| Бот | Компьютерный соперник в режиме «игрок против бота». |

## 4. Основные пользовательские сценарии

### 4.1. Создание колоды из изображений

1. Пользователь выбирает тип колоды: «Изображения».
2. Указывает количество пар в колоде.
3. Добавляет уникальные изображения по одному на пару.
4. Система проверяет формат, размер, уникальность и пригодность изображений.
5. Колода сохраняется локально на устройстве со статусом «Черновик» до проверки и публикации.
6. После успешной валидации колода получает статус «Добавлена» и становится доступной для игры.

Пример: пользователь создаёт колоду на 15 пар, загружая 15 изображений. В партии это даст 30 карточек.

---

### 4.2. Создание текстовой колоды

1. Пользователь выбирает тип колоды: «Текст».
2. Указывает количество пар.
3. Вводит текстовые значения, по одному на пару.
4. Система проверяет, что значения не пустые, не превышают лимит и не дублируются.
5. Колода сохраняется локально со статусом «Черновик» до проверки и публикации.
6. После успешной валидации колода получает статус «Добавлена».

Пример: пользователь вводит 15 слов. В партии появляются 30 карточек: каждое слово встречается дважды.

---

### 4.3. Подготовка партии

1. Пользователь выбирает режим игры.
2. Выбирает колоду со статусом «Добавлена».
3. В модальном окне выбирает нужные пары из колоды.
4. Система определяет количество выбранных пар и, соответственно, число игровых карточек: количество карточек = количество выбранных пар × 2.
5. Пользователь выбирает раскладку: строки × столбцы.
6. Система проверяет, что произведение строк и столбцов равно количеству игровых карточек.
7. Пользователь задаёт таймер, если режим и правила это поддерживают.
8. Карточки перемешиваются и выкладываются рубашкой вверх.

Пример: выбрано 12 пар → 24 карточки → допустимые раскладки, например, 2×12, 3×8, 4×6, 6×4, 8×3, 12×2.

---

### 4.4. Одиночная игра

1. Игрок открывает две карточки.
2. Если карточки совпали, они остаются открытыми.
3. Игрок получает дополнительный ход.
4. Если карточки не совпали, они закрываются после задержки.
5. Игра завершается, когда найдены все пары.
6. Показываются результаты:
   - количество найденных пар;
   - количество ходов;
   - итоговое состояние партии.

В одиночном режиме победитель не требуется. Основная метрика — прогресс и эффективность прохождения.

---

### 4.5. Игра по очереди за одним устройством

1. Перед началом партии задаётся список игроков, от 2 до 6.
2. Первый ход получает первый игрок в списке.
3. Игрок открывает две карточки.
4. Если найдена пара:
   - игрок получает 1 пару;
   - игрок ходит снова.
5. Если пара не найдена:
   - карточки закрываются;
   - ход передаётся следующему игроку по кругу.
6. Партия завершается, когда найдены все пары.
7. Побеждает игрок с наибольшим числом пар.
8. При равном числе пар фиксируется ничья.

---

### 4.6. Игра против бота

1. В партии участвуют один человек и один бот.
2. В первой версии бот имеет один базовый уровень сложности.
3. Бот не имеет доступа к закрытым карточкам.
4. Бот использует только те карточки, которые реально открывались в партии.
5. Ход бота выполняется автоматически с небольшой задержкой.
6. Правила совпадают с обычным режимом:
   - совпадение даёт боту пару и дополнительный ход;
   - несовпадение передаёт ход игроку.
7. Победитель определяется по числу собранных пар.
8. При равном числе пар фиксируется ничья.

Рекомендуемое поведение бота для первой версии:

- бот запоминает открытые карточки в пределах ограниченной памяти;
- если бот знает пару закрытых карточек, он открывает её;
- если известная пара отсутствует, бот открывает случайные закрытые карточки;
- бот не подглядывает и не использует скрытое состояние колоды.

---

### 4.7. Завершение партии

1. Партия завершается автоматически, когда найдены все пары.
2. Ввод блокируется.
3. Показывается экран результатов.
4. Для одиночного режима отображаются:
   - найденные пары;
   - число ходов.
5. Для многопользовательского режима и режима против бота отображаются:
   - пары каждого игрока;
   - победитель;
   - ничья, если победителя нет.

---

## 5. Игровые правила

### 5.1. Подготовка поля

1. Система берёт выбранную колоду со статусом «Добавлена».
2. Из каждого выбранного парой-шаблона создаёт две карточки.
3. Все карточки перемешиваются случайным образом.
4. Карточки размещаются в выбранной раскладке.
5. Все карточки изначально закрыты.

Совпадение карточек определяется не визуальным сравнением во время игры, а внутренним идентификатором пары-шаблона.

---

### 5.2. Выполнение хода

1. Текущий игрок выбирает первую закрытую карточку.
2. Затем выбирает вторую закрытую карточку.
3. Нельзя выбрать одну и ту же карточку как первую и вторую.
4. Нельзя выбрать уже найденную карточку.
5. Нельзя выбрать карточку, которая уже открыта в текущем ходе.
6. Во время анимации открытия, сравнения и закрытия карточек пользовательский ввод блокируется.

---

### 5.3. Совпадение

Если две открытые карточки имеют один и тот же парой-шаблон:

1. Карточки считаются найденной парой.
2. Они остаются открытыми до конца партии.
3. Текущий игрок получает +1 пару.
4. Текущий игрок получает дополнительный ход.
5. Очередь хода не меняется.

---

### 5.4. Несовпадение

Если две открытые карточки имеют разные пары-шаблоны:

1. Карточки остаются открытыми на 1 секунду.
2. Затем они автоматически закрываются.
3. Ход засчитывается текущему игроку.
4. Очередь хода передаётся следующему игроку.
5. В режиме против бота ход переходит от человека к боту и наоборот.

---

### 5.5. Завершение партии

1. Партия завершается, когда найдены все пары.
2. Дополнительный ход после нахождения последней пары не выполняется.
3. Результаты партии фиксируются.
4. В первой версии история партий и глобальные рекорды не сохраняются.

---

### 5.6. Определение победителя

1. В режимах с несколькими участниками каждый игрок имеет счёт пар.
2. Побеждает игрок с наибольшим числом пар.
3. Если максимальное число пар одинаково у нескольких участников, объявляется ничья.
4. Тай-брейк в первой версии не используется.

---

### 5.7. Учёт ходов

1. Ходом считается один завершённый выбор двух карточек.
2. Дополнительный ход после совпадения считается отдельным ходом.
3. В одиночном режиме число ходов отображается пользователю.
4. В многопользовательском режиме достаточно показывать счёт пар; число ходов можно показывать опционально.

---

## 6. Ограничения первой версии

### 6.1. Режимы игры

| Режим | Ограничение |
|---|---|
| Один игрок | 1 человек |
| Игроки по очереди | От 2 до 6 человек за одним устройством |
| Игрок против бота | 1 человек + 1 бот |

---

### 6.2. Количество карточек и пар

1. Количество игровых карточек всегда чётное.
2. Количество игровых карточек в партии равно: количество выбранных пар × 2.
3. В первой версии ограничиваем максимальный размер колоды для партии: минимум 2 пары, максимум 30 пар.
4. Партия использует только выбранные пары.
5. Пользовательский интерфейс предлагает все допустимые раскладки для текущего числа карточек, рассчитанные автоматически.

Пример: 12 пар → 24 карточки для игры.

---

### 6.3. Раскладка

1. Раскладка задаётся как строки × столбцы.
2. Произведение строк и столбцов должно быть равно количеству игровых карточек.
3. Допустимые значения для первой версии:
   - строки: от 2 до 12;
   - столбцы: от 2 до 12;
   - общее число карточек: не более 60.
4. Если для выбранного количества карточек нет допустимой раскладки, старт партии блокируется.
5. Пользовательский интерфейс пре��лагает только допустимые раскладки и сортирует их по близости к квадрату.
6. Допустимые раскладки вычисляются автоматически и не фиксируются в коде как отдельный список.

Примеры для 24 карточек: 2×12, 3×8, 4×6, 6×4, 8×3, 12×2.

---

### 6.4. Тип колоды

1. Колода может быть либо текстовой, либо графической.
2. Смешивание изображений и текста в одной колоде в первой версии не поддерживается.
3. Каждый парой-шаблон используется ровно один раз в рамках выбранной партии.
4. Дубликаты пар-шаблонов запрещены.
5. Пользователь может выбрать в партии любую подмножество пар из колоды.

---

### 6.5. Требования к текстовым колодам

1. Текст должен быть непустым.
2. Максимальная длина текстовой пары: 80 символов.
3. Лишние пробелы по краям удаляются.
4. Повторяющиеся пробелы внутри текста могут быть нормализованы.
5. Проверка уникальности выполняется по нормализованному значению:
   - без пробелов по краям;
   - со стянутыми пробелами;
   - без учёта регистра.
6. Разметка, HTML, BBCode и rich-text не поддерживаются.
7. Эмодзи и Unicode-символы не вводятся, так как для первой версии колоды ограничены текстом до 80 символов без эмодзи.

Пример: значения `Кот` и `кот` считаются дубликатами при создании колоды.

---

### 6.6. Требования к изображениям

1. Поддерживаются только статические изображения.
2. Анимированные форматы не поддерживаются.
3. Изображение должно быть пригодным для отображения на карточке.
4. Каждая картинка соответствует одной паре.
5. Дубликаты файлов отклоняются.
6. Пользователь не может использовать ссылку на удалённое изображение; изображение должно быть предоставлено локально.

Подробные лимиты фиксируются в ADR ниже.

---

### 6.7. Поведение интерфейса

1. Во время партии пользователь видит:
   - игровое поле;
   - текущего игрока;
   - счёт пар, если режим многопользовательский или против бота;
   - прогресс и ходы в одиночном режиме;
   - цвет текущего игрока, назначенный случайно и неизменный в рамках партии.
2. При несовпадении карточки закрываются с небольшим таймингом в 1 секунду.
3. Бот выполняет ходы автоматически.
4. Перед выходом из незавершённой партии показывается подтверждение.
5. Партия в первой версии не сохраняется после перезапуска приложения.

---

## 7. Таймер

Таймер всегда необязательный. Пользователь выбирает один из трёх вариантов:

- выключен;
- таймер на всю партию;
- таймер на ход.

### 7.1. Таймер на всю партию

- По истечении времени партия завершается.
- Победитель определяется по текущему счёту.
- В одиночном режиме показывается результат и число ходов.

### 7.2. Таймер на ход

- По истечении времени текущий ход считается неудачным.
- Временная открытая карточка закрывается. Если карточка была открыта вторая по счету, происходит переход хода.
- Если пользователь успел открыть только одну карточку, ход считается неудачным и следующим ходит следующий участник.

### 7.3. Правила таймера

1. Таймер действует только при включённом режиме.
2. Для режима против бота и для хотсит таймер на ход применим одинаково.
3. При истечении таймера во время показа карточек текущая анимация завершается, а затем применяются правила завершения хода.
4. Таймер не должен нарушать корректную логику партии.

## 8. Проектные решения по логике

### 8.1. Колода определяет набор пар, а партия — выбор подмножества

Пользователь не выбирает отдельно «карточки в партии» и «пары в колоде» как независимые сущности.

Логика такая:

1. Пользователь создаёт колоду на N пар.
2. Из колоды пользователь выбирает подходящее подмножество пар для текущей партии.
3. Система создаёт `2 × M` игровых карточек, где `M` — число выбранных пар.
4. Пользователь выбирает только раскладку для этого числа игровых карточек.

Это исключает неравномерные наборы и делает логику выбора тривиальной и прозрачной.

---

### 8.2. Совпадение определяется по идентификатору пары

Во время игры не нужно сравнивать сами картинки или тексты.

Каждая карточка имеет `pairId`. Две карточки совпадают, если у них одинаковый `pairId`.

Преимущества:

- надёжность;
- отсутствие проблем с визуально похожими изображениями;
- быстрый алгоритм;
- возможность поддерживать текст и изображения одинаковым механизмом.

---

### 8.3. Дубликаты запрещены

В первой версии каждая пара должна быть уникальной.

Причины:

- две разные пары с одинаковой картинкой или текстом будут путать игроков;
- визуально одинаковые карточки невозможно различить;
- усложняется логика пользовательских ожиданий.

Если пользователю нужно несколько одинаковых пар, это можно рассмотреть в будущем.

---

### 8.4. Бот не читает закрытые карточки

Бот должен быть честным соперником.

Разрешено:

- запоминать карточки, которые уже открывались;
- использовать историю ходов;
- открывать известные пары.

Запрещено:

- получать доступ к закрытым карточкам;
- заранее знать расположение пар;
- использовать данные, которые не были открыты в партии.

---

### 8.5. Партия не сохраняется после перезапуска

Для первой версии принимается компромисс:

- пользовательские колоды и настройки сохраняются;
- активная партия не сохраняется.

Это уменьшает сложность и снижает риск спорных ситуаций в хотсит-режиме.

---

## 9. ADR. Хранение пользовательских изображений и колод

### ADR-001. Локальное хранение пользовательских колод и изображений

Статус: принято.

#### Контекст

Приложение работает на одном устройстве, без сервера и сетевой синхронизации. Пользователь может создавать собственные колоды из изображений. Нужно решить:

- где хранить изображения;
- хранить ли оригиналы или копии;
- как связывать изображения с колодами;
- что происходит при удалении колоды.

#### Решение

1. Все пользовательские данные хранятся только локально на устройстве.
2. Метаданные колод и выбранные пары хранятся в локальном хранилище приложения.
3. Изображения хранятся как отдельные файлы в приватной области приложения.
4. При импорте изображения приложение создаёт собственную оптимизированную копию файла.
5. Приложение не должно постоянно ссылаться на исходный файл из галереи или файловой системы пользователя.
6. Файлы изображений именуются внутренними идентификаторами, например UUID, чтобы избежать коллизий и зависимости от оригинального имени файла.
7. Связь между колодой и изображением выполняется через метаданные, например:
   - `deck.id`;
   - `pair.id`;
   - `pair.imageFileId`;
   - `pair.sortOrder`.
8. Удаление колоды приводит к удалению связанных с ней файлов изображений.
9. Оптимизированные файлы могут кэшироваться для отображения, но источником истины является локальное хранилище приложения.

#### Пример структуры данных

```text
Deck
  id
  name
  type = image | text
  status = draft | added
  createdAt
  updatedAt

PairItem
  id
  deckId
  label = null для изображений
  imageFileId = путь или идентификатор файла для изображений
  sortOrder
```

#### Последствия

Положительные:

- полная офлайн-работа;
- приватность: изображения не покидают устройство;
- независимость от сервера;
- колода не ломается, если пользователь удалит исходный файл из галереи;
- проще обеспечить стабильную работу.

Отрицательные:

- данные теряются при очистке данных приложения или удалении приложения;
- нет резервного копирования в первой версии;
- может потребоваться экспорт/импорт колод в будущем.

---

## 10. ADR. Форматы, размер и обработка пользовательских изображений

### ADR-002. Ограничения размера файлов, поддерживаемые форматы и импорт изображений

Статус: принято.

#### Контекст

Пользователь может загружать собственные изображения. Нужно предотвратить:

- слишком большие файлы;
- неподдерживаемые форматы;
- повреждённые файлы;
- чрезмерное использование локального хранилища;
- проблемы с производительностью при отрисовке карточек.

#### Решение

##### 10.1. Поддерживаемые форматы

В первой версии поддерживаются только статические изображения:

1. JPEG;
2. PNG;
3. WebP.

Не поддерживаются:

1. GIF;
2. SVG;
3. BMP;
4. HEIC/HEIF;
5. анимированные изображения;
6. изображения по удалённым ссылкам.

Если платформа не может декодировать файл, импорт должен завершиться ошибкой.

---

##### 10.2. Лимиты исходного файла

1. Максимальный размер исходного файла: 5 МБ на изображение.
2. Минимальный рекомендуемый размер изображения: 256×256 пикселей.
3. Слишком маленькие изображения можно отклонять или показывать предупреждение. Для первой версии лучше отклонять, чтобы карточки оставались читаемыми.
4. Файл должен быть реальным изображением, а не файлом с изменённым расширением.
5. Проверка выполняется не только по расширению, но и по фактической возможности декодирования.

---

##### 10.3. Обработка при импорте

При добавлении изображения в колоду приложение выполняет следующие шаги:

1. Проверить формат и возможность декодирования.
2. Применить ориентацию изображения, если она задана метаданными.
3. Удалить или не сохранять чувствительные метаданные, включая EXIF.
4. Уменьшить изображение до разумного размера, достаточного для карточек.
5. Сохранить оптимизированную копию в локальное хранилище приложения.
6. Не хранить оригинальный файл пользователя в качестве основного файла колоды.

---

##### 10.4. Параметры оптимизированной копии

Рекомендуемые параметры:

1. Максимальная сторона изображения: 768 пикселей.
2. Целевой формат:
   - предпочтительно WebP, если поддерживается платформой;
   - иначе JPEG для непрозрачных изображений;
   - PNG или WebP с альфа-каналом, если нужна прозрачность.
3. Качество сжатия: около 80%.
4. Целевой размер одного сохранённого изображения: не более 300 КБ.
5. Если изображение не укладывается в лимит, система может дополнительно уменьшить качество или разрешение.
6. Если после обработки получить допустимый файл не удаётся, импорт отклоняется.

---

##### 10.5. Ограничения колоды

1. Одна колода изображений может содержать максимум 30 изображений.
2. Это соответствует максимальному размеру партии: 60 карточек.
3. Точные дубликаты файлов отклоняются.
4. Проверка дубликатов в первой версии может выполняться по хэшу файла.
5. Визуально похожие, но разные файлы разрешены, так как автоматическое распознавание сходства не требуется.

---

##### 10.6. Текстовые пары

Для текстовых колод принимаются следующие ограничения:

1. Только обычный текст.
2. Без разметки.
3. Длина: до 80 символов.
4. Значение не может быть пустым после удаления пробелов.
5. Дубликаты определяются по нормализованной строке:
   - убрать пробелы по краям;
   - стянуть повторяющиеся пробелы;
   - привести к одному регистру;
   - применить Unicode-нормализацию NFC.
6. Максимум 30 текстовых пар на колоду.

#### Последствия

Положительные:

- предсказуемый размер колод;
- быстрая загрузка карточек;
- меньше риска переполнить память устройства;
- единый подход к изображениям;
- отсутствие зависимости от внешних файлов.

Отрицательные:

- пользователь не сохраняет оригинальное изображение внутри приложения;
- некоторые файлы могут быть отклонены;
- в будущем может потребоваться более гибкая работа с изображениями.

---

## 11. ADR. Поведение после перезапуска приложения

### ADR-003. Персистентность данных после перезапуска приложения

Статус: принято.

#### Контекст

Нужно определить, какие данные сохраняются после перезапуска приложения:

1. Пользовательские колоды;
2. Изображения;
3. Настройки;
4. Активная партия;
5. Счёт в незавершённой партии.

#### Решение

##### 11.1. Что сохраняется после перезапуска

После перезапуска приложения должны сохраняться:

1. Пользовательские колоды.
2. Изображения, связанные с колодами.
3. Текстовые колоды.
4. Имена игроков, если пользователь их ввёл.
5. Последний выбранный режим игры.
6. Последняя выбранная колода.
7. Последняя выбранная раскладка, если она применима.

Это позволяет пользователю не создавать колоды заново и быстро начать новую партию.

---

##### 11.2. Активная партия не сохраняется

В первой версии активная партия не сохраняется после перезапуска приложения.

Если приложение было полностью закрыто, перезапущено или процесс был завершён системой:

1. Текущая партия теряется.
2. Приложение открывается на главном экране или на экране выбора партии.
3. Пользователю может быть предложено начать новую партию с последней выбранной колодой.
4. Счёт текущей партии не восстанавливается.

---

##### 11.3. Поведение при сворачивании приложения

Если приложение просто уходит в фон, но процесс не завершён:

1. Партия может продолжаться после возвращения в приложение.
2. Игровое состояние сохраняется в памяти процесса.
3. Если система завершает процесс, применяется правило перезапуска: партия не восстанавливается.

---

##### 11.4. Подтверждение выхода

Так как партия не сохраняется после перезапуска, при ручном выходе из незавершённой партии нужно показывать подтверждение:

> «Выйти из партии? Прогресс не будет сохранён.»

Если пользователь подтверждает выход:

1. Партия завершается или отменяется.
2. Возврат происходит в меню.
3. Счёт не сохраняется.

---

##### 11.5. Альтернатива, отклонённая в первой версии

Альтернативным решением было сохранение активной партии:

- текущий игрок;
- счёт;
- расположение карточек;
- найденные пары;
- история ходов;
- состояние бота.

Это улучшило бы пользовательский опыт, но увеличило бы сложность первой версии:

- нужно обрабатывать незавершённые анимации;
- нужно корректно восстанавливать состояние после сбоя;
- нужно решать спорные ситуации в хотсит-режиме;
- нужно тестировать больше краевых случаев.

Поэтому для первой версии принято осознанное ограничение: сохраняются только колоды и настройки, но не активная партия.

#### Последствия

Положительные:

- простая реализация;
- меньше ошибок состояния;
- нет проблем с восстановлением после сбоя;
- честная очередь хода в хотсит-режиме.

Отрицательные:

- пользователь может потерять прогресс при случайном перезапуске;
- нужен понятный текст подтверждения при выходе из партии;
- в будущем желательно добавить сохранение партии.

---

## 12. Импорт и экспорт колод

### 12.1. Контракт формата JSON

Колоды должны поддерживать импорт и экспорт в JSON. Для первой версии формат должен быть версионированный и явно валидируемый.

Минимальный контракт JSON:

```json
{
  "schemaVersion": 1,
  "deck": {
    "id": "uuid",
    "name": "My deck",
    "type": "image",
    "status": "added",
    "pairs": [
      {
        "id": "uuid",
        "sortOrder": 1,
        "label": null,
        "image": {
          "mimeType": "image/png",
          "base64": "..."
        }
      }
    ]
  }
}
```

### 12.2. Правила импорта и экспорта

1. Экспортируется полная колода.
2. Импорт должен создавать новую колоду, а не перезаписывать существующую без подтверждения.
3. JSON проверяется целиком до записи в хранилище.
4. При ошибке импорт отклоняется, а частично записанные данные не остаются.
5. При импорте изображений в JSON они кодируются в Base64.
6. Максимальный размер файла импорта должен быть ограничен по договорённости.
7. В первую версию допускается только импорт/экспорт колоды как файла JSON без внешней синхронизации.

### 12.3. Лимит файла JSON и изображений

Так как изображения в JSON будут внутри Base64, общий размер файла значительно превышает размер самих изображений. Требуется лимит файла JSON и отдельный лимит суммарного объёма перед экспортом.

Рекомендуемые ограничения для MVP:

- максимальный размер JSON-файла экспорта/импорта: 15 МБ;
- максимальный суммарный объём всех изображений в колоде: до 9 МБ в формате после оптимизации;
- экспорт/импорт должен проверять фактический размер до записи и выдавать пользователю понятное сообщение при превышении лимита.

## 13. Валидация и ошибки

### 13.1. Валидация колоды

| Проверка | Поведение |
|---|---|
| Не указано имя колоды | Использовать имя по умолчанию или потребовать ввод |
| Пустая колода | Запретить сохранение |
| Недостаточно изображений или текста | Запретить сохранение |
| Дубликат изображения | Отклонить |
| Дубликат текста | Отклонить |
| Неподдерживаемый формат изображения | Отклонить |
| Файл больше 5 МБ | Отклонить |
| Изображение не декодируется | Отклонить |
| Слишком маленькое изображение | Отклонить или показать предупреждение |
| Текст длиннее 80 символов | Отклонить |
| Текст состоит только из пробелов | Отклонить |
| Статус «Черновик» | Не запускать игру |

---

### 13.2. Валидация партии

| Проверка | Поведение |
|---|---|
| Колода пуста | Запретить старт |
| Колода повреждена | Запретить старт |
| Для количества карточек нет допустимой раскладки | Запретить старт |
| Произведение строк и столбцов не равно количеству карточек | Запретить старт |
| Выбрано недопустимое число игроков | Запретить старт |
| Не хватает локального места для сохранения изображений | Показать ошибку |
| Файлы изображений отсутствуют | Пометить колоду как повреждённую |
| Одинаковые имена игроков | Запретить старт |
| Пустые имена игроков | Подставить player-1, player-2 и т.д. |

---

### 13.3. Игровые краевые случаи

| Ситуация | Поведение |
|---|---|
| Игрок нажимает на уже открытую карточку | Действие игнорируется |
| Игрок нажимает на уже найденную карточку | Действие игнорируется |
| Игрок пытается открыть одну и ту же карточку дважды | Вторая карточка не засчитывается |
| Игрок быстро нажимает карточки во время анимации | Ввод блокируется до завершения текущего разрешения хода |
| Игрок выходит во время партии | Показать подтверждение, прогресс не сохраняется |
| Приложение уходит в фон | Если процесс жив — продолжить; если процесс завершён — партия теряется |
| Приложение перезапускается | Колоды и настройки сохраняются, активная партия не восстанавливается |
| Пользователь удаляет колоду во время активной партии | В первой версии лучше блокировать удаление или требовать завершения партии |
| Файл изображения повреждён после создания колоды | Колода помечается как повреждённая, запуск партии запрещается |
| Бот должен ходить, но произошла ошибка | Партия останавливается, показывается понятная ошибка, игрок может выйти в меню |
| Таймер закончился | Применяются правила таймера, и ход считается завершённым |

## 14. Рекомендуемая модель данных

Для первой версии достаточно следующей логической структуры.

### Deck

```text
Deck
  id: UUID
  name: string
  type: image | text
  status: draft | added
  pairCount: integer
  createdAt: timestamp
  updatedAt: timestamp
```

### PairItem

```text
PairItem
  id: UUID
  deckId: UUID
  label: string | null
  imageFileId: string | null
  sortOrder: integer
```

Для текстовой колоды:

- `label` содержит текст;
- `imageFileId` равен `null`.

Для графической колоды:

- `label` может быть пустым или использоваться как доступное описание;
- `imageFileId` указывает на локальный файл изображения.

### Настройки

```text
Settings
  lastDeckId: UUID | null
  lastMode: single | hotseat | vsBot
  lastRows: integer | null
  lastCols: integer | null
  playerNames: array<string>
```

Активная партия в первой версии не сохраняется, поэтому отдельная персистентная сущность `GameSession` не требуется.

## 15. Продуктовые ограничения, которые важно явно показывать пользователю

Чтобы пользователь понимал рамки первой версии, в интерфейсе следует отражать:

1. Максимальный размер колоды — 30 пар.
2. Максимальное число карточек в партии — 60.
3. Поддерживаются только изображения JPEG, PNG, WebP.
4. Максимальный размер исходного изображения — 5 МБ.
5. Текст — до 80 символов.
6. Прогресс партии не сохраняется после перезапуска.
7. Пользовательские колоды хранятся только на устройстве.
8. Облачная синхронизация отсутствует.
9. Импорт/экспорт JSON поддерживается для колоды, но не для активной партии.
10. Черновики нельзя использовать для запуска партии.

## 16. Рекомендуемое поведение для примера из задачи

Пример: пользователь хочет 24 карточки.

1. Система определяет: 24 карточки = 12 пар.
2. Пользователь должен предоставить:
   - 12 изображений; или
   - 12 текстовых значений.
3. Пользователь выбирает нужные пары из колоды.
4. Система создаёт 2 × M игровых карточек, где M — число выбранных пар.
5. Пользователь выбирает раскладку, например:
   - 2×12;
   - 3×8;
   - 4×6;
   - 6×4;
   - 8×3;
   - 12×2.
6. Система проверяет:
   - строки × столбцы = число игровых карточек;
   - строки и столбцы входят в допустимый диапазон;
   - колода содержит ровно выбранное количество уникальных пар.
7. Партия стартует с закрытыми карточками.

## 17. Итоговое решение для утверждения

Для первой версии принимается следующая продуктовая модель:

1. Игра полностью локальная, без сервера.
2. Пользовательские колоды хранятся на устройстве в приватной области приложения через Capacitor.
3. Колода состоит из уникальных пар-шаблонов: изображений или текста.
4. Одна пара-шаблон превращается в две игровые карточки.
5. Количество игровых карточек всегда чётное и равно `выбранных пар × 2`.
6. Минимум — 2 пары; максимум — 30 пар в одной партии для MVP.
7. Раскладка должна удовлетворять условию: `строки × столбцы = количество игровых карточек`.
8. Допустимые размеры раскладки: строки и столбцы от 2 до 12.
9. Режимы:
   - одиночная игра;
   - хотсит от 2 до 6 игроков;
   - игрок против бота.
10. Совпадение даёт пару и дополнительный ход.
11. Несовпадение закрывает карточки и передаёт ход.
12. Победитель определяется по числу пар; возможна ничья.
13. Изображения принимаются только в форматах JPEG, PNG, WebP.
14. Исходный файл изображения не превышает 5 МБ.
15. Приложение хранит оптимизированную копию изображения, а не оригинал.
16. Целевой размер сохранённого изображения — до 300 КБ.
17. Пользовательские колоды и настройки сохраняются после перезапуска.
18. Активная партия в первой версии не сохраняется после перезапуска.
19. Колоды могут быть в статусах «Черновик» и «Добавлена»; игра начинается только со статусом «Добавлена».
20. Таймер всегда необязательный: в первой версии он может быть выключен, на всю партию или на ход.
21. Импорт/экспорт колоды в JSON поддерживается и включён в фазу 0 и фазу 3.
22. В игре используется цвет текущего игрока, назначаемый случайно в начале партии и неизменный на протяжении всей партии.
