# DECISIONS.md — принятые решения (не «улучшать» без обсуждения)

1. **Слои domain / application / infrastructure / ui / app.** Хранилище можно заменить, не трогая UI и доменную логику: меняются `infrastructure` и `app/services.ts`.
2. **Порты вместо прямых вызовов** (`RawStore`, `Clock`, `IdGenerator`). Время и ID — зависимости, поэтому логика детерминирована и тестируется без моков глобальных объектов.
3. **`Result<T>` вместо исключений** для ожидаемых ошибок. Исключения не пересекают границы слоёв.
4. **Версия схемы лежит внутри данных, а не в ключе localStorage.** Миграции идут по `schemaVersion`. Данные из будущей версии отклоняются, а не портятся.
5. **Повреждённые данные не затираются.** Сначала копия в `..._backup_<ts>`. Не удалось сделать копию — запись в хранилище блокируется, пользователь решает осознанно.
6. **Загрузка состояния выполняется один раз в `main.tsx`**, до React. У неё есть побочный эффект (копия), а инициализаторы `useState` в StrictMode вызываются дважды.
7. **Запись: debounce 400 мс + `flush()`** на `visibilitychange`, `pagehide`, Capacitor `appStateChange`, unmount. Источник для записи — `stateRef` (всегда свежий), а не замыкание.
8. **Побочные эффекты не внутри `setState`-апдейтеров** (в StrictMode они вызываются дважды). Команда применяется к `stateRef.current`, затем `setState(next)`.
9. **`import/resolver` в `eslint.config.js` обязателен.** Без него eslint-plugin-boundaries не видит `.ts`-файлы и молча ничего не проверяет.
10. **Поиск: NFC, `ё→е`, регистр, пробелы.** Диакритика не удаляется, иначе «й» превращается в «и».
11. **Импорт backup приложения начинается с копии текущих данных**, имеет режимы «заменить» и «объединить» (при конфликте ID побеждает больший `updatedAt`). Файл ≤ 3 МБ. Нет копии — нет импорта.
12. **UUID с fallback** на `getRandomValues`: `crypto.randomUUID` недоступен на `http://192.168.x.x`.
13. **`androidScheme: 'https'` фиксируется один раз.** Смена схемы меняет origin WebView — localStorage «исчезнет».
14. **TypeScript 6.0, не 7**: поддержка typescript-eslint ограничена `<6.1`.
15. **Подтверждения — `ConfirmButton`, не `window.confirm`/`alert`** (в WebView ненадёжны, нарушают чистоту UI).
16. **Не реализовано сознательно:** синхронизация между вкладками (в Android одно окно; в браузере побеждает последняя запись). Если понадобится — отдельный срез с тестом.

## ADR для игры Memory

### ADR-017. Локальное хранение колод и изображений через Capacitor

**Статус:** принято.

**Контекст:** игра должна работать офлайн в Android WebView; пользовательские изображения не должны зависеть от оригиналов в галерее или облака.

**Решение:** пользовательские данные хранятся локально в приватной области приложения через Capacitor. Изображения хранятся отдельными оптимизированными файлами, имена файлов формируются из внутренних ID. Метаданные колод ссылаются на эти ID. Удаление колоды удаляет связанные изображения. Активная партия не переживает перезапуск, пользовательские колоды и настройки переживают перезапуск приложения при сохранности его локальных данных. Ошибки записи и недостаток места должны быть показаны пользователю; частично сохранённая колода не считается успешной операцией.

**Последствия:** нет сервера и сетевой зависимости; очистка данных или удаление приложения может удалить колоды. Детали API Capacitor, адаптеров, миграций, атомарности операций и обработки осиротевших файлов определяются до реализации и не должны протекать в UI/domain.

### ADR-018. Версионированный JSON-формат пользовательской колоды

**Статус:** принято для MVP; точная схема уточняется до реализации импорта/экспорта.

**Контекст:** пользователь должен переносить колоды между установками приложения вручную, без облака.

**Решение:** импорт/экспорт входит в MVP и реализуется в фазе 3. Экспортируется целая колода, включая необходимые изображения; формат JSON имеет `schemaVersion`. Импорт создаёт новую колоду, полностью валидирует файл до фиксации данных и не оставляет частично импортированные записи/файлы при ошибке. Размер файла ограничивается; ориентир MVP — до 15 МБ JSON и до 9 МБ оптимизированных изображений на колоду. Любое изменение формата требует миграционного/совместимого поведения и тестов.

**Последствия:** Base64 увеличивает размер изображений в JSON; импорт/экспорт проходит через application-порт, а платформенный выбор/сохранение файла реализуется в infrastructure. Контракт схемы, политика повторного импорта и точные лимиты должны быть согласованы перед реализацией.

Полная продуктовая спецификация и критерии поведения игры находятся в [`GAME_SPEC.md`](GAME_SPEC.md), разделы 9–12 описывают решения и экспорт/импорт.
