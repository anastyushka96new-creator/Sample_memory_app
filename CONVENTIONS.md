# CONVENTIONS.md — правила проекта (читать ПОЛНОСТЬЮ перед любой правкой)

Главный закон: правило, которое не ломает `npm run check`, будет нарушено. Поэтому почти каждое правило проверяется машиной (ESLint / tsc / Vitest). Нельзя ослаблять проверки (`eslint-disable`, `@ts-ignore`, правка `eslint.config.js`, удаление тестов) без явного разрешения пользователя.

## 1. Слои и направление зависимостей
`ui → application → domain`; `infrastructure → application, domain`; `app` видит всех.

| Слой | Что внутри | Запрещено |
|---|---|---|
| `src/domain` | Zod-схемы, чистые функции, миграции, фильтры | React, Capacitor, I/O, `Date.now`, `crypto.randomUUID`, `localStorage` |
| `src/application` | Порты и сценарии: загрузка, импорт, бэкап | React, Capacitor, импорт `infrastructure` |
| `src/infrastructure` | Реализации портов: localStorage, часы, UUID, Capacitor | React, импорт `ui` |
| `src/ui` | Компоненты и хуки React | Capacitor, `localStorage`, импорт `infrastructure` и `app` |
| `src/app` | Точка входа и сборка зависимостей (`services.ts`) | Бизнес-логика |

Новая папка в `src/` = сначала обсудить и добавить слой в `eslint.config.js` (иначе `boundaries/no-unknown-files` упадёт).

## 2. Один файл — одна ответственность
- Файл ≤ 200 строк, функция ≤ 60 строк, ≤ 4 параметров, сложность ≤ 10, вложенность ≤ 3.
- Файл приближается к 150 строкам → остановись и предложи разделение ДО добавления кода.
- Один компонент React на файл. Логика состояния — в хуке (`useXxx.ts`), не в компоненте.
- Имя файла называет его единственную ответственность; общих `utils.ts`, `helpers.ts`, `common.ts` нет.
- Не создавай файлы «на будущее». Не дублируй типы: тип выводится из Zod (`z.infer`).

## 3. Данные
- Любые внешние данные проходят через соответствующий domain-парсер: миграция → Zod → проверка целостности. Для текущего состояния приложения используется `parseAppState`; формат Memory и JSON колод имеют собственные схемы и парсеры.
- ID выдаёт порт `IdGenerator`, время — `Clock`. Доменные функции получают зависимости аргументами и остаются чистыми.
- Связи между сущностями — по ID; удаление родителя чистит дочерние данные и связанные файлы согласно ADR.
- Изменение формата сохраняемых данных требует миграции, повышения версии схемы и теста на золотом файле.
- Повреждённые данные нельзя затирать молча; восстановление/backup выполняются согласно соответствующему ADR.
- JSON пользовательских колод — отдельный сценарий, не backup всего состояния приложения.

## 4. Ошибки
- Ожидаемые ошибки возвращаются как `Result<T>` (`ok` / `err`), а не бросаются.
- Исключения перехватываются на границе с внешним миром и превращаются в `Result`.
- Пользователь всегда видит причину отказа; `console.log` запрещён.
- `any`, `as`-приведения «чтобы заткнуть компилятор», `!` (non-null) запрещены.
- Ошибка хода бота не должна молча менять текущего игрока или состояние партии: остановить игру и показать предусмотренные действия восстановления.

## 5. React
- Вычисляемое не хранится в state: фильтры, счётчики — считаются при рендере.
- `useEffect` — только для подписок и синхронизации с внешним миром, с обязательной очисткой.
- Сброс формы при смене сущности — через `key`. Список — `key={entity.id}`, не индекс.
- `dangerouslySetInnerHTML`, `eval`, `window.alert/confirm` запрещены.
- Методы интерфейсов объявляются как свойства-функции: `save: (x) => Result<void>`.

## 6. Тесты
- Новая доменная функция или сценарий = тест рядом (`name.test.ts`) в том же коммите.
- Тест фиксирует поведение, а не реализацию. Баг сначала воспроизводится тестом, потом чинится.
- Для application и ui используются подделки портов, а не реальное Capacitor-хранилище.
- Тесты случайных операций используют детерминированный `RandomSource`; тесты бота также проверяют отсутствие доступа к скрытым данным.
- Пакетный импорт изображений тестируется на принцип «всё или ничего», отмену и очистку staging.

## 7. Зависимости и версии
- Новые npm-пакеты только с разрешения пользователя. Версии зафиксированы в `package-lock.json`.
- Не используй API, в существовании которого не уверен: открой типы в `node_modules` или запроси документацию.

## 8. Протокол работы ИИ
1. Перед кодом: план (файлы, тесты, крайние случаи).
2. Меняй только файлы из утверждённого плана. Нужен другой файл — остановись и спроси.
3. Выдавай изменяемые файлы полностью.
4. После изменения структуры обнови `ARCHITECTURE.md` и `PROGRESS.md`.
5. Готово = `npm run check` зелёный. Если не удаётся исправить за 2 попытки — стоп, откат, новый чат.
6. Перед началом работы в новом чате прочитай `GAME_SPEC.md`, `GAME_SPEC_ADDENDUM.md`, `CONVENTIONS.md`, `ARCHITECTURE.md`, `DECISIONS.md` и `PROGRESS.md`.
