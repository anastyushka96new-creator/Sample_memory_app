# Регламент вайбкодинга v3

Эта версия опирается на рабочий скелет проекта (папка `vibe-app`), в котором `npm run check`
(типы → линтер → тесты → сборка) проходит, а ключевые ограждения проверены на заведомо плохом коде.
Если регламент и скелет расходятся, прав скелет.

## 0. Принцип: чем надёжнее защита, тем ниже она в списке

| Уровень | Что это | Надёжность |
|---|---|---|
| 1. Компилятор и линтер | `tsc`, ESLint: границы слоёв, лимиты размера, запрет `any` | Ломает сборку. ИИ не может «забыть» |
| 2. Тесты | Vitest: логика, сохранение, импорт, UI | Ломают сборку. Фиксируют поведение |
| 3. Pre-commit и CI | Коммит и PR невозможны при красном `check` | Ломают процесс |
| 4. Файлы правил | `CONVENTIONS.md`, `ARCHITECTURE.md` | ИИ читает, но может нарушить |
| 5. Просьбы в промпте | «Не пиши больше 200 строк» | ИИ рано или поздно нарушит |

Всё, что можно перенести с уровня 5 на уровень 1–3, переносится. То, что перенести нельзя
(например, «новые пакеты только с вашего разрешения»), в регламенте помечено как «проверяет человек».

## 1. Фаза 0. Запуск проекта (один раз)

1. Распакуйте скелет, откройте папку в VS Code.
2. PowerShell: `git init` → `npm install` → `npm run check`. Должно быть зелёное. Если красное, дальше не идите.
3. `npm run dev`, убедитесь, что приложение открывается.
4. Первый коммит: `git add .` → `git commit -m "chore: initial skeleton"`. Хук прогонит `check` сам.
5. Создайте репозиторий на GitHub и отправьте код. CI (`.github/workflows/check.yml`) заработает автоматически.

С этого момента правило одно: **в `main` попадает только зелёный `check`**.

## 2. Фаза 1. Проектирование до кода

Нейросети хорошо верстают и плохо проектируют долгоживущие данные. Поэтому сначала форма данных, потом экраны.

**Шаг 1. User Flow и сущности.** Промпт (вставляйте в AI Studio или любую модель):

```xml
<context>
Приложение: React + TypeScript, данные в localStorage, упаковка в Android.
Идея: [2-3 ПРЕДЛОЖЕНИЯ].
</context>
<instructions>
1. Выдели 2-4 экрана. Для каждого: какие данные видны, какие действия доступны.
2. Выпиши сущности, которые нужно хранить, с полями, ограничениями и связями (по ID).
3. Перечисли 5 крайних случаев (пусто, дубликаты, очень длинный текст, удаление родителя, повреждённые данные).
</instructions>
<constraints>Код не пиши. Только структурированный Markdown. В конце спроси: «Утверждаем?»</constraints>
```

**Шаг 2. Схема.** Утверждённые сущности превращаются в Zod-схемы в `src/domain/schema.ts`.
Образец уже в скелете: типы выводятся из схем (`z.infer`), лимиты вынесены в `LIMITS`, версия схемы одна.
Пока схема не утверждена вами, UI не пишется.

**Шаг 3. Что вы проверяете сами.** Для каждой сущности ответьте на три вопроса, ИИ за вас этого не решит:
- Что должно произойти с зависимыми данными при удалении? (в скелете: тег удалён, `tagId` у задач обнулён)
- Какие поля обязательны, а какие имеют разумное значение по умолчанию?
- Какой максимальный объём? Он должен лечь в `LIMITS` (localStorage ограничен ~5 МБ).

## 3. Фаза 2. Ограждения (уже настроены, ваша задача их не ослабить)

| Что защищено | Чем | Где |
|---|---|---|
| UI не лезет в хранилище, domain не знает про React | `eslint-plugin-boundaries` | `eslint.config.js` |
| «Божественные» файлы и функции | `max-lines` 200, `max-lines-per-function` 60, `complexity` 10, `max-params` 4 | `eslint.config.js` |
| `any`, `!`, неполная типизация | `strictTypeChecked`, `noUncheckedIndexedAccess`, `no-explicit-any` | tsconfig + eslint |
| Нечистая логика | запрет `Date.now`, `Math.random`, `crypto.randomUUID`, `localStorage` вне `infrastructure` | eslint |
| Заглушки вместо кода | `no-warning-comments` (`TODO`, `FIXME`, «остальной код») | eslint |
| XSS | запрет `dangerouslySetInnerHTML`, `eval` | eslint |
| Устаревшие/неверные данные | `parseAppState`: миграция → Zod → целостность | `src/domain/parse.ts` |

**Как ИИ пытается обойти ограждения и что с этим делать**

| Симптом в ответе ИИ | Реакция |
|---|---|
| Добавил `// eslint-disable`, `@ts-ignore`, `as unknown as` | Отклонить. Требовать исправить причину |
| Предлагает «ослабить правило в `eslint.config.js`» | Отклонить. Конфиг меняет только человек |
| Правит или удаляет тест, чтобы он стал зелёным | Отклонить. Сначала объяснение, почему поведение должно быть другим |
| Новый файл `utils.ts` / `helpers.ts` | Отклонить. Требовать имя по ответственности |
| Импортирует `localStorage` в компонент | Линтер не даст. Если ИИ спорит, значит, нужен новый порт (обсудить) |
| Просит установить пакет | Только с вашего разрешения: проверьте, что он существует и поддерживается |

**Честное ограничение.** Принцип «один файл — одна ответственность» машина проверяет только косвенно
(размер, сложность, границы слоёв). Дальше решает ваш глаз и ревьюер (раздел 8). Хороший признак нарушения:
у файла в описании появляется «и» («валидирует И сохраняет»).

## 4. Фаза 3. Рабочий цикл одной фичи

### 4.1. Чистый чат на каждую фичу
Новый чат. В начале вставляете **четыре файла**: `CONVENTIONS.md`, `ARCHITECTURE.md`, `DECISIONS.md`,
`PROGRESS.md` и 1–2 файла, которых коснётся задача. Больше не надо: длинный контекст ухудшает внимание.

### 4.2. Два шага: план, затем код

**Шаг 1: план (без кода).**
```xml
<context>
[ВСТАВЬ CONVENTIONS.md] [ВСТАВЬ ARCHITECTURE.md] [ВСТАВЬ DECISIONS.md] [ВСТАВЬ PROGRESS.md]
Текущие файлы по теме: [ВСТАВЬ 1-2 ФАЙЛА ЦЕЛИКОМ]
</context>
<task>Добавить: [ФИЧА ОДНИМ АБЗАЦЕМ]</task>
<plan_request>
1. Какие файлы создаются или меняются (по слоям) и зачем каждый.
2. Какие тесты пишутся (имена тестов), включая крайние случаи и ошибки.
3. Не нарушается ли какое-либо правило CONVENTIONS.md (лимиты, слои, миграции).
4. Нужна ли миграция схемы.
</plan_request>
<constraints>Код не пиши. В конце спроси: «Утверждаем план?»</constraints>
```
Вы читаете план. Проверяете: нет ли лишних файлов, предусмотрены ли ошибки, не меняется ли форма данных тайком.

**Шаг 2: код.** «Реализуй утверждённый план. Файлы выдавай полностью. Сначала тесты, затем код.
Меняй только перечисленные файлы.»

### 4.3. Вертикальный срез: порядок слоёв
1. **Домен + тест** (`src/domain`): чистая функция, `npm run test`. Коммит.
2. **Сценарий/порт** (`src/application`), если нужен внешний мир. Тест на подделках. Коммит.
3. **Инфраструктура** (`src/infrastructure`), если порт новый. Коммит.
4. **UI** (`src/ui`): сначала голые элементы, потом стили. После стилей логику не трогать. Коммит.

### 4.4. Вставка кода из чата в проект (самый частый источник ошибок)
1. Файл вставляется **целиком**, поверх старого. Никаких «вставьте этот кусок в середину».
2. Сразу `npm run check`.
3. Красное: скопируйте **полный текст ошибки** в тот же чат. Не пересказывайте.
4. Две неудачные попытки подряд: стоп (раздел 7).
5. Зелёное: проверьте руками то, что тесты не видят (внешний вид, удобство), затем коммит.

Надёжнее всего заменить копирование агентным инструментом (Claude Code, Gemini CLI, Cursor):
он сам правит файлы, запускает `npm run check` и видит ошибки. Скелет рассчитан на оба режима.

### 4.5. Definition of Done (всё машинное, кроме последнего пункта)
- [ ] `npm run check` зелёный (типы, линтер, тесты, сборка)
- [ ] Для новой логики есть тесты, включая сценарии ошибок
- [ ] Обновлены `ARCHITECTURE.md` (если менялись файлы) и `PROGRESS.md`
- [ ] Если менялась форма данных: есть миграция и тест на старом файле
- [ ] Вы сами открыли приложение и прошли сценарий

## 5. Фаза 4. Рецепты типовых изменений

**Добавить поле сущности (например, `dueDate` у задачи).**
1. Поле в `TaskSchema`, `CURRENT_SCHEMA_VERSION` +1.
2. Шаг в `MIGRATIONS[старая_версия]`: добавляет поле со значением по умолчанию.
3. Тест миграции на данных старой версии (образец: `migrations.test.ts`).
4. Только потом UI. Если пропустить п. 2, у пользователей с сохранёнными данными приложение запустится «с чистого листа».
   Поэтому `loadState` не затирает их, а делает копию, но потеря видимых данных всё равно случится.

**Новая сущность.** Схема → `LIMITS` → доменные команды с тестами → `checkIntegrity` (ссылки, уникальность) → UI.

**Заменить localStorage на другое хранилище.** Новая реализация `RawStore` в `infrastructure`,
одна строка в `app/services.ts`. Ничего больше не меняется. Если пришлось менять что-то ещё, где-то нарушены границы.

**Сделать тост/уведомление, диалог, роутинг.** Это новая зависимость. Сначала обсудить, потом оформить решение в `DECISIONS.md`.

## 6. Фаза 5. Android-релиз

```powershell
npm run check
npx cap add android        # один раз
npm run android:sync
npm run android:open       # Build → Build APK(s) для отладки
```
Чек-лист релиза (в скелете **не реализовано**, проверяйте вручную):
- [ ] Экспорт на Android через Capacitor Filesystem + Share (в WebView `<a download>` ненадёжен; порт `FileExporter` готов)
- [ ] Данные пользователя: пройдите сценарий «добавить → свернуть → убить приложение → открыть» на реальном телефоне
- [ ] `androidScheme` не менять после первого релиза
- [ ] Release-подпись: keystore в 2+ местах, не в git (`*.keystore`, `*.jks` уже в `.gitignore`)
- [ ] AAB для Google Play, `versionCode` увеличивается на каждый релиз
- [ ] Требования Google Play к `targetSdk` проверить на дату релиза в официальной документации
- [ ] Кнопка «Назад», safe-area (в CSS уже учтена), CSP, иконка и splash
- [ ] Отладка белого экрана: `chrome://inspect/#devices` → Inspect

## 7. Тупики и откат

**Правило двух страйков.** ИИ дважды не исправил одну и ту же ошибку, значит, контекст отравлен.
1. Не пишите третий промпт в этот чат.
2. Сохраните сломанное и вернитесь к рабочему:
   ```powershell
   git stash push -u -m "wip-broken"   # прячет все изменения, рабочее дерево чистое
   ```
   Хотите вообще выбросить изменения: `git restore .` и `git clean -fd` (необратимо, только если уверены).
3. Откройте новый чат, добавьте четыре файла контекста, переформулируйте задачу **более мелкими шагами**.
4. Обновите `PROGRESS.md`: что пробовали и почему не сработало («Не делать: …»). Это защищает от повторения.

## 8. Независимый ревьюер

Отдельное окно, **другая модель, если возможно**, на вход только diff и `CONVENTIONS.md`.
```xml
<context>Ты аудитор TypeScript/React. Цель: найти реальные дефекты в diff. Правила: [CONVENTIONS.md]</context>
<diff_to_review>[git diff]</diff_to_review>
<instructions>
Для каждой проблемы: серьёзность (High/Med/Low), файл:строка, КАК воспроизвести (вход → неверный результат),
способ исправления. Если не можешь описать воспроизведение, не включай пункт.
Нет проблем: ответь «Дефектов не найдено».
</instructions>
```
Ревьюер тоже ошибается. Каждый пункт проверяйте: пишете тест, воспроизводящий дефект. Красный тест = дефект настоящий.

## 9. Таблица «симптом → причина → что делать»

| Симптом | Вероятная причина | Действие |
|---|---|---|
| ИИ придумал несуществующий метод/пакет | Галлюцинация API | Отправьте текст ошибки tsc. Откройте типы в `node_modules`. Не просите «исправить», просите «покажи, где это объявлено» |
| Каждый новый ответ ломает старое | Раздутый чат | Новый чат, 4 файла контекста |
| Файл растёт, линтер ругается на размер | Нарушена одна ответственность | Разделить по смыслу до добавления функций (не «фасад ради фасада») |
| Тесты зелёные, а в приложении неверно | Тест не описывает сценарий | Добавьте тест, воспроизводящий ваш сценарий, затем чините |
| «Сохранённые данные повреждены» после обновления | Изменили схему без миграции | Копия лежит в `vibe_app_state_backup_*`. Напишите миграцию, восстановите |
| На телефоне белый экран | Ошибка JS в WebView | `chrome://inspect`, вкладка Console |

## 10. Что гарантируется, а что нет

**Гарантируется машиной** (проверено на скелете): слои не смешиваются; файлы ≤ 200 строк; нет `any`;
нет `Date.now`/`Math.random`/прямого `localStorage` в логике и UI; повреждённые данные не затираются молча;
отложенная запись сбрасывается при сворачивании; импорт не принимает дубликаты, «висячие» ссылки,
чужую версию схемы и файлы > 3 МБ.

**Не гарантируется никем:**
- что ИИ понял вашу идею правильно (проверяете вы, на этапе плана);
- что тесты описывают нужное вам поведение (их формулируете вы);
- что интерфейс удобен (смотрите глазами);
- сборка и поведение на реальном Android (проверено только логикой и тестами с подделкой Capacitor);
- «один файл — одна ответственность» (проверяется косвенно и человеком).

Эти пункты не закрываются регламентом. Они закрываются вашей внимательностью на этапах «план» и «проверка руками».
